# 配置参考（当前 main）

本页基于 `.env.example`、`apps/server/src/config.ts`、`packages/features/src/tasks/index.ts`、`packages/channel-wechat/src/index.ts` 和 `compose.yaml` 的**当前主分支实现**。日报与 Daylight 待办使用 PostgreSQL；会话、设置、通知队列和其他 Agent 数据仍使用 SQLite。请按 [快速开始](GETTING_STARTED.md) 配置真实模型后启动。产品不提供模拟体验，`faux` 仅允许在自动化测试环境中使用。

## 环境变量

模型连接统一由服务器管理员配置。桌面和浏览器的「连接与设置」仅填写后台服务器地址，并从服务器公布的模型目录中选择；界面和公开接口均不接受 Provider、供应商 Base URL、任意模型 ID 或 API Key。实例登录与模型凭据分开管理。

单模型可使用 `LLM_API`、`LLM_BASE_URL`、`LLM_MODEL` 和 `LLM_API_KEY`。多模型使用 `LLM_MODELS_FILE` 指向服务器上的 JSON 文件；该文件应限制访问权限，并置于 Web 静态目录之外。配置结构见下方「服务器模型目录」。显式目录（包括空目录）优先，其次是完整有效的 `LLM_*` 单模型配置，再兼容已存在的 SQLite / 旧 JSON 配置。环境配置不再自动复制凭据到数据库。

模型选择只保存目录标识，重启后台服务后生效。请先等待正在生成的回复结束再重启；会话与分叉后续使用所选模型，SDK 已保存的未完成生成请求仍可能引用旧模型。

尚未配置模型时仍可打开工作台和设置页，整理待办、笔记及其他数据；模型生成和后台生成任务不会启动。管理员完成服务器配置并重启后，再重新读取模型列表。启用微信通道前需先完成服务器模型配置。

公开模型接口只返回目录标识、显示名称、当前选择、当前生效项和是否等待重启，不返回供应商地址、协议或密钥。`POST /api/settings/model` 只接受 `{ "modelId": "目录标识" }`，HTTP 与 WebSocket 使用相同校验。

为兼容历史部署，未提供服务器配置时继续读取 `DATA_DIR/agent.sqlite` 中原有模型连接，旧 `DATA_DIR/model-settings.json` 在成功写入 SQLite 后迁移删除。客户端只记录模型选择，不再修改这些连接或凭据。显式服务器配置优先于历史存储；历史记录仍应随数据目录和备份按凭据管理。

### 业务数据库与旧数据迁移

服务启动必须提供 `DATABASE_URL`。Compose 使用 `pgvector/pgvector:pg16`，不向宿主机发布数据库端口；API 通过内部地址 `postgres:5432` 连接。分别生成 `POSTGRES_ADMIN_PASSWORD` 与 `POSTGRES_APP_PASSWORD`，并将后者填入 `DATABASE_URL`；具体变量见 `.env.example`。初始化脚本仅在新数据卷首次启动时执行；已有卷需单独创建业务账号与 `vector` 扩展，修改环境变量不会重设数据库密码。

启动时自动将 `DATA_DIR/agent.sqlite` 的日报和 `DATA_DIR/daylight.sqlite` 的 Daylight 数据导入 PostgreSQL。保留项目、任务、排序、删除标记、历史导入标记、幂等动作结果，以及日报正文、版本和时间。每个源独立事务导入，冲突整体回滚；成功记录源路径标记，之后不重复导入，旧文件保留且不再写入业务数据。

测试使用 `NODE_ENV=test` 和 `DATABASE_URL` 指定的数据库；每个临时数据目录使用独立 schema。测试账号需有该数据库的 `CREATE` 权限；不要指向生产业务库。

### 服务器模型目录

在服务器设置 `LLM_MODELS_FILE=/etc/pi-assistant/models.json`，文件为以下数组结构：

```json
[
  {
    "id": "primary",
    "name": "主模型",
    "provider": "openai-completions",
    "baseUrl": "https://your-provider.example/v1",
    "model": "your-model-id",
    "apiKey": "YOUR_OWN_KEY",
    "contextWindow": 128000,
    "maxTokens": 8192
  }
]
```

`id` 是唯一的客户端选择标识；`name` 可省略，默认显示 `id`。每项的协议、地址、模型与密钥均须完整，`contextWindow` 和 `maxTokens` 可省略，默认分别为 `128000` 和 `8192`，且输出上限不得超过上下文窗口。目录为空数组时没有可选模型；缺失、重复标识或格式错误会使启动报错，不回退使用旧连接。单模型环境配置及旧记录的目录标识统一为 `default`。

目录文件由管理员在服务器维护，修改后重启后台。容器部署时需将文件以只读方式挂载，并把 `LLM_MODELS_FILE` 设为容器内路径；不要将其放进前端静态目录或提交真实密钥。客户端提交 `{ "modelId": "primary" }` 只记录选择，原有连接配置保持由服务器管理。

### 最小可运行配置

**真实模型配置：**

```dotenv
LLM_API=openai-completions
LLM_BASE_URL=https://your-provider.example/v1
LLM_API_KEY=YOUR_OWN_KEY
LLM_MODEL=your-model-id
```

请用真实供应商参数替换占位符。该项目通过显式提供 `baseUrl` 和 API 协议类型接入模型，**不能保证所有 OpenAI 兼容中转都支持图像、工具或相同的模型字段**。供应商不支持的能力不要默认当作项目已支持。

### 生产部署最低配置

```dotenv
DEMO_PASSWORD=REPLACE_WITH_A_STRONG_RANDOM_PASSWORD
LLM_API=openai-completions
LLM_BASE_URL=https://your-provider.example/v1
LLM_API_KEY=YOUR_OWN_KEY
LLM_MODEL=your-model-id
```

使用 `docker compose up -d --build`。生产未配置 `DEMO_PASSWORD` 会拒绝启动，不能通过移除鉴权来解决。默认容器映射只绑定到 `127.0.0.1`，需要远程访问时应另外部署 TLS 反向代理。

### 浏览器会话与 cpolar

以下会话机制适用于默认启用鉴权的部署。自用时可在 API 服务环境中显式设置 `AUTH_DISABLED=1` 并重建 API；使用共享 API 网络的微信桥也须随之重建。无需删除原密码，也不要改成开发模式。移除该开关并重建服务后恢复原密码登录；只清空密码但不启用该开关，生产启动仍会拒绝。既有 cpolar 网关的首页子请求在此模式下返回成功，不再要求登录。

验证成功的 Basic `GET /api/info` 会签发一小时有效的签名 Cookie（`__Host-pi-durable-session`，Secure/HttpOnly/SameSite=Strict，Path=/），不在 Cookie 内保存口令。HTTP 和 WebSocket 使用同一个后端鉴权器；显式错误 Authorization 优先拒绝，不回退到 Cookie。签名密钥只在当前服务器实例内存中，服务重启后需重新建立会话。

现有 cpolar HTTP 隧道会丢弃 WS 的 Authorization，但保留 Cookie；[公网网关配置](../deploy/cpolar/nginx.cpolar.conf) 在返回首页前验证 Basic 并引导浏览器保存 Cookie，无需新增密钥环境变量或自有域名。重连时会话已过期可刷新主页，必要时重新输入原口令。必须通过 HTTPS 使用；不要删除口令、在 URL/query 中传口令，或把所有上游请求固定注入认证头。部署状态与操作步骤见 [cpolar 公网部署](DEPLOYMENT.md#7-直接使用-cpolar-公网访问2026-10-26)。


## 运行模式与可选通道

`POST /api/crash` 已移除，通过鉴权的同源请求在所有环境返回 404；旧 `ENABLE_CRASH_DEMO` 配置不再生效。自动化测试可以显式使用 `NODE_ENV=test` 和 `LLM_API=faux`，正式服务和桌面应用不使用该模式。

**通知：**不配置 `NOTIFY_WEBHOOK_URL` 时后台任务照常进行，只是不产生外部通知。Webhook / 飞书事件先写入 SQLite，再异步发送；详见下方[通知队列与失败记录](#通知队列与失败记录)。Webhook 对端应按 `X-Pi-Event-ID` 去重。

**微信：**默认不开启。启用前分别用 `openssl rand -hex 32` 生成 `WECHAT_WEBHOOK_KEY` 与 `WECHAT_SEND_TOKEN`，将 `WECHAT_ENABLED=1` 放入 `.env`，按 [微信接入手册](WECHAT.md) 使用 `--profile wechat` 启动。微信扫码凭据保存在专用 Docker 命名卷，不应导出到仓库。

**笔记检索：**设置 `OBSIDIAN_ROOT` 后，助手只能只读检索白名单笔记，回答带来源路径和行号，不会写回 Obsidian。默认只开放 AI学习、X灵感、VPS小白教程；财务、个人档案和服务器资产不在范围内。这与未合并的 [PR #4](https://github.com/xiaomoBoy/pi-durable-assistant/pull/4) 不是同一份代码。

**工作区审批：**仍在待验收的 [PR #5](https://github.com/xiaomoBoy/pi-durable-assistant/pull/5) 中。当前 `main` 没有对应配置，请勿按待合并分支的参数尝试启用。

## 通知队列与失败记录

通用 Webhook 和飞书共用 `DATA_DIR/agent.sqlite` 中的 `notification_outbox` 表，与微信发送队列独立，不需要新增配置或依赖。提醒、计划和后台任务在提交完成检查点前先入队；同一目标和事件 ID 只保留一份正文，成功后重放也不会重新入队。

- 服务运行时每秒检查待发队列，每次最多处理 20 条。单次发送超时 8 秒；最多尝试 5 次，失败后的间隔依次为 15 秒、1 分钟、5 分钟、15 分钟。重启后恢复待发记录；发送中崩溃的尝试也计数，其记录在 30 秒租约到期后继续处理。
- 网络故障、超时、HTTP 408/429/5xx 及飞书 HTTP 成功但业务 `code` 非零或响应不合法时重试；其他非成功 HTTP 状态直接记为失败。达到上限后停止自动发送，保留 `failed` 记录；可在「设置 → 通知投递」查看并手动重新投递。
- 可重试的 HTTP 错误若带有有效 `Retry-After`（整数秒数或 HTTP 日期），下次投递取接收端指定时间和本地退避时间中较晚的一个，并持久保存，重启不提前发送。无效、已过期或较短的值不缩短本地退避；仍最多尝试 5 次。
- `NOTIFY_MODE` 在新事件入队时过滤；`off`、未配置 URL 或 `PI_OFFLINE=1` 时不发送已排队事件。重新启用会继续待发队列；从 `all` 改为 `errors` 不删除此前已入队的正常事件。
- URL 与消息格式共同决定目标指纹，数据库不保存 Webhook URL。更换 URL 或格式不会把旧消息发往新目标；旧队列保留，恢复原配置后可继续。失败详情仅保存固定类别或 HTTP 状态码，不保存原始异常、URL 或接收端正文。
- 设置中的免打扰按 IANA 时区计算，普通事件延后；明确失败、内部结构化 `urgent` / `approval` 事件立即投递，不会被较早普通事件挡住。不根据文案关键词猜紧急程度。事件优先级单独持久化，不改变 generic / 飞书原始正文；旧 generic 失败与审批正文可迁移，旧飞书正文没有结构化优先级，无法从正文可靠补建。`off` 仍关闭全部投递。Webhook 默认继续逐事件发送。可在「免打扰与 Webhook 摘要」中显式启用 `webhookDigest`（默认 `enabled=false`、`windowSeconds=60`；窗口允许 10–3600 整数秒）。仅启用后新入队的普通事件按固定时间窗口汇总，免打扰期积压在允许时段合并；紧急、失败、审批仍单独优先投递。generic 摘要保留 `id/type/text/failed/at`，其中 `type=digest`、`at` 为 ISO 时间，并追加原始 `events` 数组；飞书使用文本摘要。接收端须先支持该可选协议。
- 可在「免打扰与 Webhook 节奏」显式启用 `webhookAttention`（默认 `enabled=false`、`maxPerHour=6`、`cooldownSeconds=300`），不自动更改已有提醒授权。普通通知的首次投递每滚动小时最多 1–60 次，相邻投递冷却可设为 0–3600 整数秒；超出仅延后，不删除、不消耗重试次数。摘要计一个投递单元。预算在 SQLite 中按目标原子预留，重启、多个连接和网络结果未知不会重置；同 ID 的网络或人工重试不重复占预算，但仍遵守网络退避。关闭后立即恢复原策略。
- 失败、结构化紧急与审批事件、定时提醒和周期计划不受新增注意力预算限制。提醒与计划仍按原有免打扰及已启用的摘要规则处理；混合摘要含提醒时整份摘要保留提醒时序。来源可验证的旧飞书或不透明正文缺少分类时，保守保留原时序；缺少来源信息的旧待发／失败记录不会自动发送或重试，正文与 ID 仍保留以供审计。分类只用结构化元数据，不从正文关键词猜紧急程度。此预算仅适用于 Webhook／飞书，不改变 Outlook 和 Teams 自动提醒。
- 待发送列表额外提供 `delivery` 分级及原因（就绪、免打扰、冷却、滚动小时预算、摘要窗口或网络重试），`nextAt` 表示当前策略下最早可投递时间，可能受更早队列或后续设置变化影响，不承诺精确送达。预算延后不会伪装成投递失败。来源失效或无法验证的记录可在「已撤销」筛选查看，不能人工重新投递。在途请求无法撤回：若远端随后明确确认成功，记录会更新为已送达，并注明撤回发生得太晚；返回 HTTP／业务错误与网络结果未知保留各自类别，停止后续尝试并提示可能已经送达。不会声称已送到外部的消息已被收回。
- 每摘要同时受 100 成员与完整 JSON UTF-8 字节预算限制（飞书 16KiB，generic 32KiB），超出拆成独立摘要；单事件包装后超预算时按原 ID 和原正文单独投递，不截断。这不是所有接收端限制的保证。
- 摘要 ID、正文和成员列表在 SQLite 事务内固定；成员源记录保留，状态、次数、退避与摘要原子同步。列表按投递单元展示，可查看 `memberIds`；按摘要或成员 ID 重试均重试整个固定摘要。关闭摘要不拆分已创建摘要，未聚合记录保留已排定窗口。网络结果未知可能重复，稳定 ID 仅供接收端去重，不是端到端恰好一次。Webhook 完成事件没有通用的外部“已处理”回执，不从网页已读标记推断业务已处理或擅自撤销。
- 已发送和失败记录目前不自动清理，以保留去重与排障依据；通知正文包含任务内容，与数据库备份一起按私有数据管理。
- 管理界面默认查看失败记录，可切换全部、待发送、已送达和失败；每种视图显示当前目标最近 100 条记录，每 5 秒自动刷新，也可手动刷新。只展示事件 ID、状态、次数、时间、策略解释和脱敏错误，不返回正文、URL 或目标指纹。
- 只有当前目标的失败记录可以重新投递：保留原事件 ID、正文及创建时间，清空上一轮错误和完成时间，尝试次数归零，重新获得最多 5 次投递机会。操作先持久入队，再由后台发送；“已入队”不表示已送达。待发送和已送达事件不能重发；关闭通知、未配置 URL 或离线时拒绝重试。重新投递仍可能重复送达，接收方需按事件 ID 去重。

管理 API 沿用 Basic Auth 和同源写保护，不依赖模型配置：

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET | `/api/notifications` | 当前目标最近 100 条；可选 `status=pending\|sent\|failed\|cancelled`，先筛选再限制条数；非法状态返回 400 |
| POST | `/api/notifications/retry` | JSON `{ "id": "事件 ID" }`；成功入队返回 202；非法 ID 返回 400，不存在或属于其他目标返回 404，停用或非失败状态返回 409 |


本机可只读查看最近记录（将路径替换为实际数据目录，不要输出 `body`）：

```bash
sqlite3 -readonly /path/to/data/agent.sqlite 'SELECT id, status, attempts, last_error FROM notification_outbox ORDER BY created_at DESC LIMIT 50;'
```

`pending` 表示等待首次发送或重试，`sent` 表示接收端已确认，`failed` 表示永久拒绝或次数耗尽。发送已成功但本地尚未记账即崩溃仍可能重复投递；接收方应使用 `X-Pi-Event-ID` 去重，generic JSON 也包含同一 `id`。飞书机器人不保证按此 Header 去重。本功能不承诺端到端恰好一次或必达；代码任务本身仍不具备重启恢复能力，尚未入队的完成通知也无法凭空补建。

## 安全建议

- 不提交 `.env`、服务商 Key、微信数据卷备份和包含鉴权信息的日志。
- 项目是单用户原型，不提供多租户隔离、SSO 或多用户权限矩阵；尽量只通过自己控制的 HTTPS 入口访问。
- 模型费用可能产生在供应商/中转平台；**项目内 `cost: 0` 占位不等于免费**，建议在上游平台设置预算和额度限制。
- 只下载/接入信任的模型或服务地址；不要把私有文件附件发送给不信任的模型提供商。
- 对持久化 SQLite 和微信状态卷进行一致性备份；参考 [部署手册](DEPLOYMENT.md)。

## Outlook / Microsoft 365 邮件（当前工作区）

桌面端和浏览器均在「设置 → Outlook 邮件」管理同一后端。令牌、缓存和同步游标只保存在后端数据目录；桌面端只经 API 读取通知。

### 复用已有公司账号

后端用 `MAIL_ACCOUNT_FILE=/绝对路径/teams-forward-config.json` 指定本地账号文件，不自动探测旧桌面目录。文件中的 `account` 需已有 `tenantId`、`clientId`、`username`、`password` 四个字符串，网页不接收或显示密码，也不另存一份密码。无需复制账号信息到聊天或邮件设置。

仅在**当前实例从未保存过邮件配置**且找得到该文件时，自动启用邮件监听、申请 `Mail.Read offline_access` 并开始同步。已有手动配置、已保存的暂停或断开操作不会被启动覆盖。设置页的「使用现有账号连接」可显式重新启用或切换回已有账号；连接完成后后台自动同步，通常用刷新令牌续期，不每分钟提交密码。

这是微软密码授权（ROPC），只能在公司策略允许时使用，不支持 MFA 挑战。密码错误、MFA/条件访问要求、授权失败或刷新令牌被撤销时会停止自动密码重试，**重启也不会重新撞密码**；核对原配置后手动重连，或改用下方交互授权。单次进程内密码登录至少间隔一分钟。选择交互登录后不会悄悄回退到密码方式。

重启或手动重连时重新读取账号来源，检测到租户、应用或用户名变化会先清空旧邮件、通知、令牌与游标，为新账号建立静默基线；运行中修改来源文件需手动重连或重启。密码轮换不改变邮箱身份。不要依赖缓存状态来确认公司策略仍允许登录。

### 手动配置应用并交互授权

1. 请公司管理员在 Microsoft Entra ID 注册适用于公司租户的应用，取得 **Directory (tenant) ID** 和 **Application (client) ID**。设置页只接受这两个 UUID；不填邮箱密码或客户端密钥。
2. 在应用的「Authentication → Advanced settings」启用 **Allow public client flows**，配置 Microsoft Graph **委托权限 `Mail.Read`**。程序另外请求 `offline_access` 用于刷新令牌；若公司要求，请先完成管理员同意。不需要 `Mail.ReadWrite`、`Mail.Send` 或应用级邮箱权限。
3. 在设置页填写 Tenant ID、Client ID，勾选「启用邮件监听」并保存，再点击「登录微软邮箱」。
4. 打开页面显示的微软授权链接，输入一次性代码，使用公司账号完成登录和 MFA。小 D 会后台轮询授权结果，成功后自动同步。代码过期可重新登录。

这一替代入口是设备代码登录，不使用原配置中的密码。若公司条件访问策略禁止设备代码流，或要求特定受管设备，此流程仍可能被拒绝；不能用关闭 MFA 解决，需由管理员确认是否允许这种接入方式。首版只支持微软全球云，公司中国云或政府云不在范围内。

### 查询与提醒

- 同步范围是授权账号的 **收件箱**，首次仅获取近 **30 天**邮件。之后使用 Microsoft Graph delta，每分钟左右检查一次；分页较多、网络错误或限流会延迟，限流遵守 `Retry-After`。
- 首次同步是建立基线，不提醒历史邮件。后续新进入收件箱的邮件产生通知，更新已读状态、修改已有邮件不会重复通知。缓存及游标按页一起落盘，正常重启不重复入库。
- 可以问「查看最新邮件」「今天张三发了哪些邮件」「找主题包含报价的未读邮件」「读一下这封邮件的正文」。工具为 `outlook_messages` 和 `outlook_read`，查询前会尝试同步，失败时明确说明只读本地缓存与最后同步时间。
- 本地缓存最多保留 90 天；邮件列表默认最多 20 封、单次最多 50 封；正文只保存纯文本，最多 20000 字。如果 Graph 未按要求返回纯文本，则只保留纯文本预览，不呈现 HTML 或加载外部图片。附件仅展示是否存在，不下载。
- Web 在页面打开时显示新邮件横幅；桌面端另有系统通知，macOS 窗口关闭但应用仍运行时也可提醒。需要允许系统通知。服务端复用「设置 → 通知投递」中的免打扰时区和时段，已明确为普通/低重要性的新邮件等待最多约 1 分钟形成摘要（再加客户端轮询延迟），静默期内继续积累，结束后只展示一批摘要，不按 50 条分页补弹。Microsoft Graph `importance=high` 邮件立即触发一次合并摘要，普通积压可一同列入该次摘要；预览优先显示重要邮件。旧增量游标可能缺少新选取的 `importance` 字段，这类邮件保守即时提示而不猜测紧急程度。提醒不自动写进聊天，也不转发微信或 Webhook。
- 投递前按最新本地同步状态剔除已读或移出收件箱的来源；取消结果在通知保留期内持久化，重新标为未读不会恢复旧提醒。实际处理状态仍受 Graph 同步延迟影响，读取正文不等于已处理，也不会修改微软已读状态。
- 升级后的 Web 与桌面共用服务端持久交付队列，以摘要 ID、45 秒独占租约和展示确认协调，正常情况下只提示一端。确认落盘后服务重启不重放，未确认摘要在租约到期后可由健康端接续。展示与确认无法原子提交：展示后确认未落盘就崩溃或断网，接续仍可能重复，优先避免静默丢提醒。
- 网页隐藏时不领取、不确认；回到前台后继续。桌面需收到系统展示事件后才确认，不支持系统通知时不参与领取，失败或超时由其他端接续。系统展示回执不等于用户已经阅读。
- 旧 GET 客户端不参与共享交付，混用时仍可能重复。新版客户端需要支持共享交付的新版后端，不会静默回退旧 GET。当前账号首次启用共享交付时，服务端持久记录历史基线；之后新设备、网页刷新和全部客户端重启均继承未交付积压，不能跳过仍在合并窗口或免打扰中等待的来源。升级旧交付状态时保留已有客户端最早基线，切换账号或清除缓存后重新建立。服务端重新领取时重查已处理项目，尚未同步的邮箱操作或已经返回的在途内容无法撤回。
- 通知来源最多保留 7 天，交付队列不保证超过来源保留期仍可展示。退出桌面仅停止桌面轮询，后端仍同步；停止后端才停止邮件监听。

### 暂停、退出与数据处理

取消「启用邮件监听」并保存，会停止当前同步并保留登录和缓存。重新启用即可恢复。点击「断开并清除缓存」会停止监听，清除当前实例中的邮件、通知记录、令牌与增量游标，但保留应用 ID。更换 Tenant ID / Client ID 或重新登录也会先清空旧账号缓存，防止不同账号混用数据；首次重建不补发历史提醒。微软端的授权仍需在微软账号/企业应用中撤销。

增量游标过期（Graph HTTP 410）时，会清掉失效缓存并重新建立近 30 天基线，避免已移出或删除的邮件长期残留。重建期间不会提醒历史邮件。

令牌和邮件在 `DATA_DIR/agent.sqlite` 的 `outlook_*` 表内明文保存，沿用数据目录与数据库的私有文件权限。接口不返回账号密码、用户名、配置文件路径、访问令牌、刷新令牌或设备授权私码，仅返回登录方式、账号文件是否可用及交互登录需用户输入的一次性代码与授权链接。数据目录及其备份应按凭据管理；清除当前缓存不会清除备份、已生成的对话或模型供应商已收到的内容。对话查询邮件时，查询结果会进入你配置的模型上下文。第三方邮件只能作为资料，不能代替用户指令或授权。

`PI_OFFLINE=1` 会强制禁止 Outlook 登录与后台同步，即使保存配置已启用且已有令牌也不联网，仍可读缓存和清理本地数据。测试真实数据副本时必须开启。

### 本地接口

以下接口与其他 API 共用 Basic Auth、同源写保护和 WebSocket 请求入口：

| 方法和路径 | 用途 |
| --- | --- |
| `GET /api/settings/mail` | 读取配置、登录状态、同步时间与错误；不返回令牌 |
| `POST /api/settings/mail` | 保存 `{enabled, tenantId, clientId}`，立即生效 |
| `POST /api/mail/login` | 切换为交互授权并申请设备代码，返回后自动后台轮询 |
| `POST /api/mail/login-account` | 显式使用本地已有账号连接并启用监听，不接收密码或文件路径 |
| `POST /api/mail/refresh` | 尝试立即同步，离线或停用时不联网 |
| `POST /api/mail/disconnect` | 停止监听并清除当前账号缓存和令牌 |
| `POST /api/mail/delivery` | 新版客户端用 `{clientId}` 领取共享摘要，返回独占 `delivery.id/token/leaseUntil`；每账号首次启用建立历史基线，之后所有客户端共享未交付积压 |
| `POST /api/mail/delivery/ack` | 仅展示后用 `{clientId,id,token}` 确认；可幂等重试，旧租约不能确认新租约 |
| `GET /api/mail/notices` | 获取当前通知游标，不补发历史 |
| `GET /api/mail/notices?after=<序列>` | 获取服务端策略放行的邮件摘要；`items` 最多 50 条预览，`total` 为摘要总数，`cursor` 为下一次 `after`，`urgent` 表示含高重要性邮件。空批也须按 `cursor` 推进，不能以最后一条样本代替摘要水位 |

真实公司租户的应用注册、管理员同意、MFA/条件访问与实际邮件投递需在配置后现场验收；本地自动化测试只使用假的 OAuth/Graph 响应，不代表租户已经授权。


## Teams 自动提醒的免打扰与合并

- Teams 转微信复用同一免打扰设置。规则命中的普通来信默认等待 30 分钟后合并；每批最多 12 个来源，以限制模型输入和手机消息长度，普通批次至少间隔相同的摘要窗口。窗口可在「今天 → Teams 待处理 → 同步设置」调整。明确 `importance=high/urgent` 的来源仍沿用已有紧急投递策略；未知或旧来源缺少重要性字段时按普通消息处理，不再绕过免打扰，不从正文猜紧急。普通用户问答和审批交互不按自动提醒延迟。
- 摘要成员与输入在注入前持久化。注入确认丢失、重启或新来信不会重新组合旧来源；使用相同来源的持久请求 ID 重试，避免重新生成同一提醒。部分来源失效时，模型输入与最终投递均只使用复核后有效的原文，原成员 ID 保持不变以避免重复注入。已授权的工作状态自动代回不受通知免打扰影响；入口与实际 POST 前都会重查授权和来源，等待凭据期间已回复、撤销、推送或过期的来信不再代回，未知发送结果保护继续有效。
- 首次注入、最终微信投递和重试前均核对来源：已回复、Graph 已标删除、超过 24 小时提醒窗口的来源撤销；混合摘要只重建仍有效的原文，不沿用已失效的建议草稿。刷新失败先保留；整体同步成功也不能替本轮未核对或已失去访问权限的来源聊天背书。免打扰延期不消耗微信发送尝试；转发在下一轮 Teams 采集后重新检查，实际延迟受工作/非工作周期和故障退避影响。
- 用户已处理但尚未同步到后端的动作，以及已开始的网络发送，不能即时撤回。微信网络结果未知时仍可能重复，不能保证端到端恰好一次；正式应用使用带来源的持久微信队列。旧宿主若只提供逐条 `inject` 回调，继续逐条兼容；直接桥接发送以稳定 `X-Pi-Event-ID` 提供去重线索，是否去重取决于桥接端。
- 复核发现已缓存来源正文发生变化时，保守撤销其自动提醒，不继续注入旧正文。现有聊天缓存并非完整的远端编辑同步；这项保护只防止延迟提醒使用已观察到变更的旧来源，不能撤回此前已经注入或开始投递的内容。


## Teams 主动同步与待办建议

「今天 → Teams 待处理」提供来源可核对的建议列表，不需要打开微信，也不调用模型。它只使用已配置 Teams 账号采集到的聊天缓存；没有配置 `TEAMS_CONFIG_DIR`、离线模式或权限不足时不会连接真实 Teams。自动采集覆盖既有聊天范围与重要性规则，不会自动扩大到全部团队频道，也不申请新的 Graph 权限。

### 默认节奏与控制

- 工作日周一至周五，09:00–18:00，时区 `Asia/Shanghai`：每轮结束后约 2 分钟采集一次。
- 其余时段：约 15 分钟一次。历史归档独立每 30 分钟一轮，最多 20 页；已观察到的旧消息编辑和删除仍经过来源撤回流程。
- 普通微信摘要窗口默认 30 分钟。采集频率与提醒频率分开，后台查到新消息不等于逐条打扰用户。
- 页面中可以保存工作日、时区、时段及频率。工作频率为 1–60 分钟，非工作为 5–120 分钟，归档为 5–1440 分钟、摘要为 5–720 分钟（留出 24 小时来源窗口内的投递余量）。非工作和归档不得比工作采集更频繁。后台每 15 秒只读取本地设置，不在每次检查时请求微软；不同工作时段和设置改变会重新计算下一轮时间。
- 关闭自动同步会停止新一轮后台采集，在途请求可能完成；手动刷新、用户主动查询和确认待办前的来源核对仍可读取。离线模式禁止这些联网读取。手动刷新仍遵守微软限流。
- 失败指数退避最长增长到 1 小时，但不缩短用户更慢的周期或微软 `Retry-After`。429/503 会停止本轮采集，同一服务进程的实时同步、历史归档和精确原文读取共享账号级 Graph 限流门闩，不能轮换读取路径继续撞限流；限流门闩不跨服务重启保存。聊天 403/404 会隐藏该来源建议，约一小时后允许重新核对；完整聊天列表中消失的来源同样隐藏，分页失败不会假设其已消失。

### 建议不是自动执行

- 最近 24 小时的未回复重点来信最多显示 100 条，超过时明确标注。列表显示发送者、聊天、时间、原文预览及可用的微软原始链接。同步失败或资料不新时显示缓存状态，不把上次成功时间当成逐条新鲜度保证。
- 只有直达私聊或明确提及本人、带行动请求的消息才建议建待办。对方明确标高优先级并且有直达行动请求时提示「优先核对」，不是系统已经确认紧急。正文时效词未核实时归「信息不足」，不猜截止时间；缺乏即时证据不等于不急。未知内容、FYI、否定请求不能自动生成任务。
- 用户点击「确认创建待办」才写入 Daylight 收件箱。服务器先刷新聊天、核对该聊天确实成功读取，再单独读取精确源消息，比较源版本，并在事务写入后再次核对。源已回复、编辑、删除、失去权限或刷新失败时不创建。重复点击、响应丢失与重启使用同一来源幂等键，不重复建任务，也不复活被用户删除的任务。
- 任务默认只含通用跟进标题和原始消息链接，不复制第三方正文、推测截止日期或替用户承诺。可以在 Daylight 中补充自己的行动描述。已创建的任务属于用户自己的清单，不因一次回复或来源撤回自动完成/删除。来源校验与 PostgreSQL 提交并非跨库原子操作：最终写入复核之后、提交期间或提交后发生的撤回不会自动删除这个不含原文的用户任务。
- 「忽略」对该消息持续有效，不会因同聊天别的消息编辑而复活；「稍后提醒」只让建议在两小时后重新进入页面列表，不新增系统弹窗或定时发送。
- 当前「已回复」沿用已有保守聊天状态：同聊天后续本人发言会隐藏此前的来信建议，不能等同于行动项已经完成，群聊尤其应核对。这一版没有语义级任务完成识别。
- Teams 自动通知不能通过 `todo`、`create_task` 等模型工具修改 Daylight。工具按持久调用对应的原始输入检查，后来的用户消息不会给较早的通知调用补授权。用户本人之后明确请求的正常任务操作不受影响；自动 Teams 通知也不能通过委派、后台任务、提醒或计划重新包装文本后写入清单。计划/后台任务的应用派生输入目前不作为 Daylight 写入授权，需本人另行确认。
- 本功能不自动发送 Teams 回复，不开启新微信/Webhook/系统通知渠道。已配置的微信转发及已明确授权的工作状态代回继续使用原有来源检查和发送保护。

本地 API：`GET /api/teams/triage` 返回列表、来源版本、同步状态和设置；`POST /api/teams/triage/refresh` 手动采集；`POST /api/teams/triage/settings` 接受完整 `{settings}`；`POST /api/teams/triage/act` 接受 `{id, revision, action: "create" | "dismiss" | "snooze"}`。所有写操作沿用身份认证与同源保护。设置和建议处理决定存于 `agent.sqlite`，正式任务和幂等结果存于现有 PostgreSQL。

升级提醒：旧版本缺少重要性字段时的即时转发已改为普通摘要；普通摘要默认窗口从 1 分钟改为 30 分钟，新消息/归档不再固定每 45 秒轮询。升级不重置水位、不重发已确认的摘要、不自动创建任务，也不会覆盖旧隐私来源记录。真实租户权限、网络请求成本、手机送达和生产部署需要单独验收。
